SECTION 1: SESSION OVERVIEW
--------------------------------------------------------------------------------

This session covered the full planning and implementation of the multi-file data
pipeline for BGO Report Factory. Starting from a working single-file upload flow,
the session expanded the system into an 8-step pipeline with deep profiling,
schema relationship detection, hybrid AI interview (Flow 1), checkable KPI
selection, data validation, and story-driven dashboard generation.

Reference documents used:
  - claude_plan.md      — approved implementation plan
  - PRD3.md             — product requirements (single source of truth)
  - PROJECT_PLAN.md     — historical project state

--------------------------------------------------------------------------------
SECTION 2: USER PROMPT / REQUIREMENTS
--------------------------------------------------------------------------------

Framework & Deployment
  - Build on ADK framework (Python only — no GCP/AWS dependency)
  - Deploy on Railway

End-to-End Workflow (8 steps)
  1. Multi-file upload — batch CSV + Excel simultaneously
     Capture: filename, type, size, row count, column names, sample rows,
     null counts, duplicate counts
  2. Deep file profiling — detect encoding (chardet), delimiter (csv.Sniffer),
     sheet names for Excel, data type per column
  3. Schema mapping per file — AI auto-classifies Dimension/Measure/Date/Key
     User can edit. AI suggests grain-level columns (multi-select)
  4. Schema relationship detection across files — column name match,
     fuzzy matching, cardinality match, value set overlap
  5. AI interview (side panel chatbot) — Q1 hard-coded (domain identification),
     Q2+ dynamic based on uploaded column profiles
  6. KPI suggestion — scrollable checkable LIST (not card grid)
     User checks/unchecks. Allow custom KPI addition
  7. AI data validation — zero-value fields, missing data, division risks
  8. Dashboard generation — story-driven sections, not a random KPI dump

KPI Registry & Templates
  - JSON-based KPI registry
  - Templates pre-built: client health, collections, CX, executive dashboard
  - Each template defines: ID, name, required KPIs, optional KPIs,
    chart types, section layout

Frontend requirements
  - Batch file upload replaces single file upload
  - Each file gets its own tab (column table, data type, semantic role, grain)
  - Progress sidebar showing per-file completion
  - "Continue to KPI Selection" enabled only when all files are done
  - KPI selection: scrollable checkable list with slicer/filter style (NOT card grid)
  - Double-click to add comment; Select All / Deselect All
  - Dashboard: KPIs grouped into story sections

Backend requirements
  - POST endpoint accepting multiple files at once
  - CSV: CSV sniffer for encoding + delimiter (never assume comma-separated)
  - Excel: detect sheet names, handle multiple worksheets
  - Upload limits: Excel 200,000 rows, CSV 200,000 rows, 50MB per file
  - SQLite for now, PostgreSQL-ready
  - Dynamic table schema — do not create one table per upload
  - Plan for data appending and crash recovery

LLM Model Support
  - GPT-4o-mini (OpenAI) — default
  - claude-sonnet-4-20250514 (Anthropic) — alternate
  - Switch via LLM_PROVIDER in .env — no code change required

AI Interview Flows
  - Flow 1 (build first): Q1 hard-coded generic question, Q2+ dynamic
  - Flow 2 (deferred): fully dynamic — DO NOT start until Flow 1 is tested

SECTION 3: PLAN DECISIONS & CLARIFICATIONS
--------------------------------------------------------------------------------

Q: What about the interview question structure?
A: Q1 is always hard-coded ("What type of data does this represent?").
   Q2 onwards are AI-generated dynamically based on the uploaded column
   profiles (detected dates, measures, dimensions). This is still Flow 1.

Q: What is the Excel row limit?
A: 200,000 max (same as CSV).

Q: Is schema mapping mandatory before interview?
A: No. Schema mapping page has two CTAs:
   "Continue to Interview" and "Skip Interview → Go to KPI Selection".
   Interview is optional at all steps.

SECTION 5: BUG FIXED DURING SESSION
--------------------------------------------------------------------------------

Issue: Files uploaded but showed "Failed" status with no error message in UI.
       Backend terminal showed no errors.

Root cause (confirmed):
  1. chardet module was not installed in the backend virtual environment (new-env).
     The `import chardet` at the top of parser.py crashed the background profiling
     task immediately. The exception was caught silently by _parse_and_profile()
     and stored in upload.error_message — but error_message was not included in
     UploadResponse, so the frontend could not display it.

  2. Alembic migration 0002 had not been applied. The staging_tables table was
     created by Base.metadata.create_all() (which only creates new tables, never
     alters existing ones), so the 5 new columns (encoding, delimiter, sheet_names,
     active_sheet, grain_columns) did not exist in dev.db. Any INSERT with those
     columns would have failed.

Fixes applied:
  - Confirmed chardet==5.2.0 already in new-env (was installed, just not on PATH python)
  - Ran: alembic stamp 0001 (DB created via create_all, not alembic — no version record)
  - Ran: alembic upgrade head (applied migration 0002 — added 5 new columns)
  - Added error_message to UploadResponse schema so frontend can display actual errors
  - Added error_message to UploadStatus polling in upload/page.tsx
  - Added _run_migrations() to main.py startup (prevents this class of failure after
    future schema changes — alembic upgrade head runs automatically on server start)

Verification:
  - Confirmed columns exist: encoding, delimiter, sheet_names, active_sheet, grain_columns
  - Confirmed all imports work in new-env
  - Backend restarted; uploads processed successfully

SECTION 6: DATABASE MIGRATION NOTES
--------------------------------------------------------------------------------

If dev.db was created BEFORE this session (via Base.metadata.create_all), run:

  cd backend
  alembic stamp 0001           # tells alembic the DB is already at revision 0001
  alembic upgrade head         # applies migration 0002 (adds new StagingTable columns)

Going forward, main.py calls alembic upgrade head automatically on every startup,
so manual migration runs are no longer needed for new team members.
